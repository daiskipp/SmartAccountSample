## ペルソナ

### ペルソナ1: 本人ユーザー

- **役割**: Smart Accountの所有者。RPG風プロダクトのエンドユーザー
- **目的**: パスキー紛失・端末故障などの「もしものとき」に備えて、自分のアカウントへのアクセスを失わないようにしたい
- **技術レベル**: 初級〜中級（暗号技術の詳細は理解していない前提。技術用語を出さないUIを必要とする）

### ペルソナ2: ガーディアン（友人）

- **役割**: 本人ユーザーから信頼され、L3の友人ガーディアンリカバリに参加する第三者。自身もSmart Accountのユーザーである想定
- **目的**: 友人（本人ユーザー）が困ったときに、なりすましでないことを確認したうえで手助けしたい
- **技術レベル**: 初級（招待コードの受け取り・承認操作程度の簡単な操作のみ想定）

> 運営側承認担当者は本Planでは「システム内部インターフェース（API/DB）」としてのみ扱い、UIペルソナとしては
> 定義しない（社内承認UI・ワークフローは別スコープ、`requirements.md` CON-006/CON-010参照）。

## エピック1: L1 バックアップ鍵（ふっかつのじゅもん）

### US-001: じゅもんを発行して保管する 🔵

**私は** 本人ユーザー **として**
**オンボーディング中に「ふっかつのじゅもん」を発行し、一度だけ確認して安全に控えたい**
**そうすることで** パスキーを紛失してもアカウントにアクセスできる保険を持てる

- **関連要件**: FR-101, FR-102, FR-103, FR-104, FR-406, FR-002
- **優先度**: Must Have
- **受入基準**: AC-001

### US-002: じゅもん由来鍵でログインを復旧する 🔵

**私は** 本人ユーザー **として**
**パスキーを紛失した際に、じゅもんから導出した鍵でアカウントへアクセスしたい**
**そうすることで** 主端末を失っても資産やデータへのアクセスを失わない

- **関連要件**: FR-103
- **優先度**: Must Have
- **受入基準**: AC-002

## エピック2: L2 マルチデバイスペアリング

### US-101: 既存端末からもう1台を追加する 🔵

**私は** 本人ユーザー **として**
**既存端末で「デバイスを追加」を選び、ペアリング用のQR/コードを提示したい**
**そうすることで** 新しい端末を安全に自分のアカウントに紐付けられる

- **関連要件**: FR-111, FR-116, FR-404
- **優先度**: Must Have
- **受入基準**: AC-003, AC-005

### US-102: 新端末をQR読み取りでペアリングする 🔵

**私は** 本人ユーザー **として**
**新端末のカメラでQRコードを読み取ると、ログインしていなくてもそのまま参加画面（`/device/join`）が開き、そこでローカルに鍵交換して新しい端末をセットアップしたい**
**そうすることで** 手元にある別の端末からもアカウントを使えるようになる

- **関連要件**: FR-112, FR-113, FR-114
- **優先度**: Must Have
- **受入基準**: AC-003

### US-103: SASを目視確認してなりすましを防ぐ 🔵

**私は** 本人ユーザー **として**
**両方の端末に表示された確認コード（SAS）が一致することを目視で確認したい**
**そうすることで** 悪意ある第三者の端末が紛れ込んでいないことを確信できる

- **関連要件**: FR-113, FR-114, FR-115
- **優先度**: Must Have
- **受入基準**: AC-003, AC-004

### US-104: 端末一覧を管理し、紛失端末を取り除く 🔵

**私は** 本人ユーザー **として**
**登録済み端末の一覧をニックネーム付きで確認し、紛失した端末を削除したい**
**そうすることで** 紛失端末経由での不正アクセスのリスクを断てる

- **関連要件**: FR-005, FR-117, FR-118
- **優先度**: Must Have
- **受入基準**: AC-006

## エピック3: L3 友人ガーディアン（自己主権ソーシャルリカバリ）

### US-201: 信頼できる友人をガーディアンとして招待する 🔵

**私は** 本人ユーザー **として**
**信頼できる友人2〜5人を招待コードでガーディアンとして登録し、必要な承認人数（Threshold）を設定したい**
**そうすることで** 運営に頼らず、自分の知る相手だけでアカウントを復旧できる仕組みを持てる

- **関連要件**: FR-121, FR-122, FR-123
- **優先度**: Must Have
- **受入基準**: AC-007

### US-202: ガーディアンとしてリカバリ依頼を確認・承認する 🟡

**私は** ガーディアン（友人） **として**
**友人からリカバリの依頼が来たら、承認状況を確認しながら自分の承認を行いたい**
**そうすることで** 友人が困っているときに安心して手助けできる

- **関連要件**: FR-124
- **優先度**: Must Have
- **受入基準**: AC-008

### US-203: Threshold成立でsignerが自動的に差し替わる 🔵

**私は** ガーディアン（友人） **として**
**必要人数の承認が揃った時点で、システムが自動的にRule#0のsigner差し替えを実行してくれることを期待したい**
**そうすることで** 承認後の手続きを自分たちで意識せずに復旧が完了する

- **関連要件**: FR-125, FR-126
- **優先度**: Must Have
- **受入基準**: AC-008

## エピック4: L4 運営ガーディアン（所持証明型リカバリ）

### US-301: 運営サポートに申し込み、秘密Sを保管する 🔵

**私は** 本人ユーザー **として**
**「運営のサポートを頼る」を選び、一度だけ表示される秘密Sをオフラインで保管したい**
**そうすることで** 個人情報を渡すことなく、運営に見せる「もしもの鍵」を持てる

- **関連要件**: FR-131, FR-132, FR-133, FR-134, FR-135
- **優先度**: Must Have
- **受入基準**: AC-009, AC-010

### US-302: 秘密Sを送らず所持を証明してリカバリを依頼する 🔵

**私は** 本人ユーザー **として**
**パスキーも他の手段も失ったとき、秘密Sを送信せず端末内のchallenge署名で所持を証明してリカバリを依頼したい**
**そうすることで** 最終手段として運営の助けを借りてアカウントを取り戻せる

- **関連要件**: FR-136, FR-137, FR-138, FR-405
- **優先度**: Must Have
- **受入基準**: AC-011, AC-012

### US-303: 待機期間中に身に覚えのないリカバリを止める 🔵

**私は** 本人ユーザー **として**
**自分が依頼していないリカバリが進行していたら、待機期間中に既存の手段でキャンセルしたい**
**そうすることで** 万一の不正なリカバリ依頼からアカウントを守れる

- **関連要件**: FR-140, FR-155
- **優先度**: Must Have
- **受入基準**: AC-017, AC-018, AC-019

### US-304: 公開ステータスページで進行状況を確認する 🔵

**私は** 本人ユーザー **として**
**ログインしなくても、リカバリが進行中かどうかと残り時間を確認したい**
**そうすることで** 万一の際にすぐ異常に気づき、必要なら対処できる

- **関連要件**: FR-156, FR-202
- **優先度**: Must Have
- **受入基準**: AC-020

### US-305: 待機期間が満了しリカバリが確定する 🔵

**私は** 本人ユーザー **として**
**異議がなければ待機期間の満了後、新しいThreshold認可を行い、システムにリカバリを確定してほしい**
**そうすることで** 運営が不在・応答不能でも、自分の他の手段でアカウントを取り戻せる

- **関連要件**: FR-003, FR-139, FR-141, FR-151, FR-152, FR-153, FR-154
- **優先度**: Must Have
- **受入基準**: AC-013, AC-014, AC-015, AC-016, AC-021

## エピック5: 横断・オンボーディング体験

### US-401: 「もしものとき」の備えを段階的に案内される 🔵

**私は** 本人ユーザー **として**
**アカウント作成直後に、じゅもん発行→ペアリング→ガーディアン/運営選択の順で無理なく案内されたい**
**そうすることで** 難しい判断を迫られずに、必要な分だけ備えを整えられる

- **関連要件**: FR-301, FR-302, FR-303
- **優先度**: Must Have
- **受入基準**: AC-001, AC-003, AC-007, AC-009

### US-402: 技術用語を意識せず状況を理解する 🔵

**私は** 本人ユーザー **として**
**「Context Rule」「Threshold Policy」のような専門用語ではなく、柔らかい言葉でリカバリの状態を理解したい**
**そうすることで** 不安を感じずに自分のアカウントの安全性を把握できる

- **関連要件**: FR-004
- **優先度**: Must Have
- **受入基準**: AC-020

## ユーザージャーニー

### ジャーニー1: オンボーディングから備え完了まで（本人ユーザー、brief §5-1準拠）

```
アカウント作成完了 → じゅもん発行(強く推奨) → もう1台の端末を追加？(任意)
      US-401              US-001                    US-101/US-102/US-103
         → 友人にお願い／運営に頼る／今は設定しない(任意・選択式) → ステータス画面
              US-201/US-301         US-401                          US-402
```

### ジャーニー2: パスキー紛失からの復旧（本人ユーザー、L1のみ設定済みの場合）

```
パスキー紛失に気づく → じゅもんを取り出す → じゅもん由来鍵でログイン → 復旧完了
                            US-002               US-002
```

### ジャーニー3: 友人ガーディアンによる復旧（本人ユーザー＋ガーディアン）

```
本人: 全端末喪失に気づく → ガーディアンにリカバリ依頼を伝える
ガーディアン: 依頼確認 → 承認 (US-202) → Threshold成立 → signer自動差し替え (US-203) → 本人が新パスキーでログイン
```

### ジャーニー4: 運営ガーディアンによる復旧（本人ユーザー）

```
本人: 全端末喪失 → Sを端末内で使ったchallenge署名でリカバリ依頼 (US-302) → [サーバー: commit照合→4-eyes承認→運営署名]
   → 待機期間開始・ステータスページで確認 (US-304) → (異議あれば)cancel_recovery (US-303)
   → 異議なく満了 → リカバリ確定 (US-305) → 新パスキーでログイン
```
