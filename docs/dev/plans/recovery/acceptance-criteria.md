## AC-001: [FR-101〜104, FR-406] じゅもんの発行と一度限りの表示 🔵

**関連**: FR-101, FR-102, FR-103, FR-104, FR-406, US-001

### Given（前提条件）
- ユーザーがオンボーディング中で、Rule#0には既存パスキーのみが登録されている

### When（実行条件）
- ユーザーが「じゅもん発行」を選択し、表示された単語列を確認して確認チェックを完了する

### Then（期待結果）
- クライアント側で128bit以上のエントロピーの単語列が生成・表示される
- 単語列からEd25519/P-256鍵ペアが導出され、その公開鍵がRule#0にsignerとして追加される（既存signerは維持）
- 確認後、単語列は画面・メモリから破棄され、再表示する手段が提供されない

### テストチェックリスト
- [ ] **正常系**: じゅもん発行→鍵導出→Rule#0への追加が一連で成功する 🔵
- [ ] **正常系（L1統合）**: じゅもん発行→Rule#0追加→パスキー紛失を想定→じゅもん由来鍵でログインが成功する 🔵
- [ ] **異常系**: 確認チェック未完了のまま画面遷移しようとした場合、単語列を保持したままにしない（再表示不可を維持） 🟡
- [ ] **境界値**: エントロピーが128bit未満になる単語列生成ロジックが存在しないことを検証する 🟡

## AC-002: [FR-103] じゅもん由来鍵によるログイン復旧 🔵

**関連**: FR-103, US-002

### Given（前提条件）
- ユーザーがL1のじゅもんを発行済みで、じゅもん由来鍵がRule#0のsignerとして登録されている

### When（実行条件）
- ユーザーが主パスキーを紛失し、じゅもんから再導出した鍵で認証を試みる

### Then（期待結果）
- じゅもんから同一の鍵ペアが再導出され、Rule#0のsignerとして認証に成功する

### テストチェックリスト
- [ ] **正常系**: 正しいじゅもんの単語列からの再導出でログインが成功する 🔵
- [ ] **異常系**: 単語列を1語でも誤って入力した場合、鍵導出結果が異なりログインに失敗する 🔵
- [ ] **境界値**: 単語の順序を入れ替えた場合にログインが失敗すること（順序依存の導出であること）を確認する 🟡
- [ ] **互換性**: 固定wordlist・NFKD・checksum・HKDF・domainの既知ベクトルがブラウザとRust実装で一致する 🔵

## AC-003: [FR-111〜114] ペアリングとSAS確認による端末追加 🔵

**関連**: FR-111, FR-112, FR-113, FR-114, US-101, US-102, US-103

### Given（前提条件）
- 既存端末にRule#0のsignerとしてパスキーが登録済み

### When（実行条件）
- 既存端末で「デバイスを追加」を選択しQR/コードを表示、新端末でそれを読み取りローカルでECDH鍵ペア生成・共有秘密導出後、両端末でSASを目視確認する

### Then（期待結果）
- 両端末に同一のSAS（6桁程度）が表示され、ユーザーが一致を確認すると新端末でパスキー登録が行われ、その公開鍵が既存端末の署名でRule#0に追加される

### テストチェックリスト
- [ ] **正常系（L2統合）**: ペアリング→新端末接続が成功し、新端末のsignerがRule#0に追加される 🔵
- [ ] **異常系**: ペアリング中に通信が中断した場合、中間状態のsignerが追加されない 🟡
- [ ] **境界値**: ペアリング用トークンの有効期限直前・直後での挙動差（AC-005参照） 🟡

**関連**: FR-113, FR-115, US-103

### Then（期待結果）

### テストチェックリスト
- [ ] **正常系（L2統合）**: SAS不一致→追加ブロックが確認できる 🔵
- [ ] **異常系**: 中間者攻撃を模した共有秘密の差し替えを行っても、SASが一致しないため検知できる 🟡
- [ ] **異常系**: role・session・transcript・追加対象passkeyの差し替え、片側だけの確認、暗号文replayが拒否される 🔵

## AC-007: [FR-121〜123] ガーディアン登録とRule#Recovery(L3)作成 🔵

**関連**: FR-121, FR-122, FR-123, US-201

### Given（前提条件）
- ユーザーがオンボーディングまたは設定画面から「信頼できる人にお願いする」を選択している

### When（実行条件）
- 招待コード等で2〜5人のガーディアンを登録し、Threshold値Mを設定する

### Then（期待結果）
- 新規独立Rule#Recoveryが作成され、signers=登録ガーディアン集合、policies=Threshold(M-of-N)が設定される。M>N、M<2は登録画面でエラーとなる

### テストチェックリスト
- [ ] **正常系**: 2〜5人のガーディアン登録とThreshold設定でRule#Recoveryが作成される 🔵
- [ ] **異常系**: M>Nとなる設定を試みるとクライアント側バリデーションで拒否される 🔵
- [ ] **境界値**: M=2（推奨最小値）、N=5（上限）での設定が成功する 🟡
- [ ] **異常系**: クライアントを迂回しても`M < 2`、`M > N`、`N > 5`、重複guardian、無効addressが各信頼境界で拒否される 🔵

## AC-009: [FR-131〜135] L4申し込みと秘密S発行・commit送信 🔵

### テストチェックリスト
- [ ] **正常系**: S生成→commit計算→サーバー送信→Rule#Recovery(L4)設定が一連で成功する 🔵
- [ ] **異常系**: commit計算前にネットワーク送信APIが呼ばれるパスが存在しないことを検証する（S非送信の設計検証） 🔵
- [ ] **境界値**: Sの表示は1回のみで、画面遷移後は再表示不可であることを確認する 🟡

### Given（前提条件）
- L4のRule#Recoveryが3signer（運営・独立した本人第二要素鍵・L1じゅもん由来鍵）Threshold(2)構成で、運営が応答不能（不在）とみなされる状況

### When（実行条件）
- 運営票を除く2要素（独立した本人第二要素鍵・L1じゅもん由来鍵）のみで署名を揃える

### Then（期待結果）
- 運営票なしでもThreshold(2)が成立し、TimeDelayPolicyの待機期間を経てリカバリが確定する

### テストチェックリスト
- [ ] **正常系（L4統合）**: 運営票を除く2要素のみでThreshold(2)を達成しリカバリが確定する（運営不在時の可用性） 🔵
- [ ] **異常系**: 1要素のみ（運営票もなし）ではThreshold(2)が成立しないことを確認する 🟡

## AC-022: [FR-002, FR-401] 秘密材料の非送信検証（全レベル横断） 🔵
